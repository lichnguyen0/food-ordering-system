# Plan for Implementing Address Profile Feature in Checkout

## Goal
Allow users to save multiple addresses (e.g., home, office) and select one during checkout, making the "Hồ sơ" (Profile) section functional.

## Steps

### 1. Database Design
- Create a new table `user_addresses` to store address information for each user.
- Fields: 
  - id (PK)
  - user_id (FK to users)
  - label (e.g., "Home", "Office")
  - recipient_name
  - phone_number
  - address_line
  - ward
  - district
  - city
  - zip_code
  - is_default (boolean)
  - created_at
  - updated_at

### 2. Backend Changes
- Create an `Address` entity class.
- Create an `AddressRepository` interface extending JpaRepository.
- Create an `AddressService` class with methods:
  - List addresses for a user.
  - Get an address by ID (ensuring it belongs to the user).
  - Save a new address.
  - Update an existing address.
  - Delete an address.
  - Set an address as default (if needed).
- Create an `AddressController` REST controller with endpoints:
  - GET /api/addresses -> list of addresses for the logged-in user.
  - POST /api/addresses -> create a new address.
  - PUT /api/addresses/{id} -> update an address.
  - DELETE /api/addresses/{id} -> delete an address.
  - (Optional) PUT /api/addresses/{id}/default -> set as default.

### 3. Frontend Changes
- In `src/main/resources/templates/order/checkout.html`:
  - Replace the static "Hồ sơ" section with a dynamic dropdown that:
    - Shows a placeholder (e.g., "Chọn hồ sơ") when no address is selected.
    - Populates the dropdown with the user's addresses (fetched via AJAX on page load).
    - Allows the user to select an address.
    - Updates a hidden input field (e.g., `<input type="hidden" name="addressId" id="addressIdInput">`) with the selected address ID.
  - Ensure the dropdown UI matches the existing design (similar to the payment method dropdown).
- In `src/main/resources/static/js/checkout.js`:
  - Add a function to fetch the user's addresses from `/api/addresses` on page load.
  - Render the addresses in the dropdown list.
  - Handle the selection of an address (similar to the payment method dropdown):
    - Update the dropdown header with the selected address's label (or a formatted string).
    - Update the hidden input field with the address ID.
  - Ensure the form submission includes the addressId.

### 4. Integration with Order Creation
- Modify the `CheckoutRequest` DTO (if it exists) to include an `addressId` field (or keep the existing address/detailAddress fields as fallback).
- In the `OrderService` (or wherever the order is created):
  - If `addressId` is provided, fetch the address from the database and use its full address for the order's delivery address.
  - Otherwise, fall back to the existing behavior (using `address` and `detailAddress` fields).

### 5. Additional Considerations
- Security: Ensure that users can only access their own addresses.
- Error handling: Show appropriate messages if address fetching fails.
- UI/UX: Consider allowing users to add a new address from the checkout page (maybe a modal or a link to the address management page).
- Default address: Optionally, pre-select the user's default address (if any) on page load.

### 6. Testing
- Write unit tests for the new service and repository.
- Test the API endpoints.
- Test the checkout flow with different address selections.
