# Plan: Post-order routing — GrabFood-like UX

## Objective
Define a professional after-order flow: confirmation landing and live order tracking, aligning with GrabFood-like UX.

## Scope
- Frontend routing and UI for order confirmation and tracking
- Backend endpoints for order detail and tracking events
- Real-time updates approach (polling vs WebSocket)
- Security: ensure order data access is scoped to the authenticated user

## Proposed flow
1) After a user places an order, show an Order Confirmation page with: order number, restaurant, item list, total, and an ETA. Include a prominent "Track Order" CTA and a "Back to home" option.
2) Provide a tracking route. Users can open tracking from the confirmation page or navigate later via a bookmarked URL.
3) Optionally auto-redirect from confirmation to tracking after a short delay (configurable).
4) The Tracking page displays a live progress timeline (RECEIVED, PREPARING, ON_THE_WAY, DELIVERED), ETA, and driver details. Include a map if feasible.

## Routes (backend and frontend)
- POST /api/orders — create a new order
- GET /api/orders/{orderId} — order details (security-scoped by user)
- GET /orders/{orderId} — order details page (frontend)
- GET /orders/track/{orderId} — order tracking page (frontend)
- Optional: WebSocket /stream/orders/{orderId} or SSE for live updates
- Optional polling: GET /api/orders/{orderId}/status

## Data model considerations
- Order: id, userId, restaurant, items, total, status, eta, driver
- Status lifecycle: RECEIVED -> PREPARING -> ON_THE_WAY -> DELIVERED
- Ensure idempotent reads and consistent ETA handling

## Frontend changes
- After order creation, navigate to /orders/{orderId} or /orders/track/{orderId} with a confirmation banner
- Implement TrackOrder component with timeline, ETA, and optional map
- Reuse existing UI components for consistency; ensure accessible and responsive design

## Backend changes
- Add authorization checks on GET /api/orders/{orderId}
- Expose endpoints for order tracking state and optional live updates
- Emit status changes to connected clients if real-time updates are enabled

## Testing strategy
- End-to-end: place order, arrive at confirmation, open tracking, see progress
- Verify unauthorized access is blocked
- Validate ETA updates propagate to client (polling or push)

## Milestones
1) API contract defined (order detail, tracking)
2) Frontend routes and components implemented
3) Tracking UI with timeline and ETA
4) Real-time updates implemented (optional) and tested
5) End-to-end tests added

## Risks and mitigations
- Real-time updates complexity: start with polling, add WebSocket later
- Privacy: ensure order data access restricted to owner
- Map integration: optional feature gated behind availability

## Acceptance criteria
- User lands on a confirmation page with orderId and ETA
- User can reach a dedicated tracking page via CTA or bookmark
- Tracking shows status progression and ETA; unauthorized access is blocked

## Questions for stakeholders
- Do you prefer automatic redirect to tracking from the confirmation page? If yes, after how many seconds?
- Which route should be the canonical tracking URL: /orders/{orderId} (details) or /orders/track/{orderId} (tracking UI)?
- Is map integration required in MVP or optional?
